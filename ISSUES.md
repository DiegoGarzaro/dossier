# Dossier — Issue & Tech-Debt Ledger

> Master ledger of every **gap, bug, or improvement** discovered while building Dossier.
> This is the source of truth for defects and debt; forward-looking scope/tasks live in [`PLAN.md`](PLAN.md).

**Working agreement:** the moment something is discovered — even if unrelated to the current task,
even if fixed immediately — it gets a row here. Never fix silently or rely on memory.

- **Type:** `Bug` (broken behaviour) · `Gap` (missing but planned) · `Improve` (works, could be better)
- **Severity:** 🔴 high · 🟠 med · 🟡 low
- **Status:** `open` · `in progress` · `done (YYYY-MM-DD)`
- **Ids** are stable: append as `G-NN`, never renumber or reuse. Close an item by setting its status to `done` (keep the row for history).

| G-40 | Bug | 🔴 | Security | Found in review of the encrypted backup: `crypto.decrypt()` unpacked the Argon2id cost parameters from the archive header and passed them straight to the KDF **with no bounds check**. `memory_cost` is a `uint32`, so a crafted `.dossier` file could demand ~4 TiB of RAM; a forged header asking for 512 MiB (8× the default) was honored without complaint in a live test. Binding the header as AAD — which the implementation does correctly — does **not** cover this: it stops a *downgrade* of someone else's archive, but an attacker simply generates their own file with their own passphrase and absurd parameters, and the tag is valid for it. The tag doesn't even matter, because the expensive derivation runs **before** authentication can fail, so any garbage with a large number at bytes 13–16 forces the allocation. One small POST to `/api/restore` OOMs a single-container app; a bit-flip in that field on a corrupted download does it accidentally. Fixed by validating `time_cost`/`memory_cost`/`parallelism` against sane bounds immediately after unpacking and before deriving, rejecting (never clamping — a silent clamp derives the wrong key and reports it as a bad passphrase, which is a lie). Bounds: `time_cost` 1–10, `memory_cost` 8–262144 KiB, `parallelism` 1–16, applied on **encrypt** as well so the app can never mint an archive its own `decrypt` refuses to open. Re-verified after the fix: headers demanding 512 MiB, 2 GiB, and the uint32 maximum (~4 TiB) are all rejected in ~0.0000s, before any derivation, and legitimate archives still open. 8 new tests. | done (2026-08-01) |

| G-38 | Gap | — | Import | JSON import built (Phase 3, FR-30 / G3): `POST /api/import` consumes the G-34 envelope. **Additive by design — never destructive:** no deletes, no renames, no overwrites. People are matched by exact `full_name`; a match is skipped (counted + warned) and the file's links are reconnected to the existing record, which makes a re-import a no-op rather than a vault-duplicator. Imported people are built field-for-field from the file *without* the usual seeding, since the export already carries the system fields (seeding would double every built-in). `value_omitted` fields import blank and are counted, so a withheld secret can never null out a stored one (SEC-7). | G-37 | Bug | 🟠 | Fields | Found while adding the Date of birth field: **type validation was silently skipped on every field update.** `validate_value` compared with `is` (`field_type is FieldType.number`), but `PersonField.type` is a plain `String` column, so a field read back from the database carries a `str` — and `"number" is FieldType.number` is False.
